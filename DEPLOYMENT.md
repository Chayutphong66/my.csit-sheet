# Production deployment

CSIT Sheet is deployed as one Render web service. Express serves both the Vue build and `/api` from one HTTPS origin. A Render persistent disk stores the SQLite database; uploaded files are already stored as deduplicated BLOBs in that database, so the same disk preserves accounts, refresh sessions, documents, versions, and file bytes.

This is intentionally a single-instance architecture. Render persistent disks cannot be shared by multiple instances and disk-backed services do not use zero-downtime deploys. Move the database and file assets to managed services before horizontal scaling.

## Render Blueprint

The tracked `render.yaml` creates:

- a Node 24.21.0 web service in Singapore on the smallest paid 0.5 CPU / 512 MB plan;
- a 1 GB persistent disk mounted at `/var/data`;
- an automatically generated `JWT_SECRET`;
- a database-aware health check at `/api/health`.

Deploy from the repository in the Render dashboard using **New > Blueprint**, then select this repository and approve the resource plan. The paid plan and disk require the repository/account owner to confirm billing. Do not create a free service: a free instance cannot attach the required persistent disk.

The service runs `npm ci && npm run build`, then `npm run start:production`. On every start, the production bootstrap:

1. refuses to run without an absolute `DATABASE_PATH`;
2. copies an existing database to `/var/data/csit-sheet.sqlite.predeploy-backup`;
3. applies idempotent schema migrations;
4. imports the tracked CS and IT registrar workbooks only when that exact workbook hash has not already completed;
5. never creates demo users.

## Environment variables

The Blueprint supplies generated/default values and prompts the owner for `ALLOWED_ORIGINS`. Enter the exact Netlify production origin (for example, `https://site-name.netlify.app`, with no trailing slash). Variable names are documented here; secret values must stay in Render and must never be committed.

| Variable | Requirement | Purpose |
| --- | --- | --- |
| `NODE_ENV` | required | Must be `production`. |
| `DATABASE_PATH` | required | `/var/data/csit-sheet.sqlite`, on the persistent disk. |
| `JWT_SECRET` | required, secret | Random signing secret generated by Render. |
| `ACCESS_TOKEN_TTL` | optional | Access-token lifetime; Blueprint uses `15m`. |
| `REFRESH_TOKEN_TTL_DAYS` | optional | Refresh-session lifetime; Blueprint uses `7`. |
| `PORT` | platform supplied | Render's HTTP port. |
| `HOST` | optional | Production defaults to `0.0.0.0`. |
| `ALLOWED_ORIGINS` | required for Netlify | Exact Netlify production origin, or comma-separated HTTPS origins. The service's Render URL is allowed automatically. |
| `FRONTEND_URL` | optional | Another explicit frontend origin, if one is introduced later. |
| `VITE_API_URL` | not needed here | Build-time API base for a separately hosted frontend. Same-origin production uses `/api`. |

## Verification after the first deploy

1. Open `/api/health` and confirm `{"status":"ok","database":"ready"}`.
2. Open `/`, refresh a nested SPA route, and confirm assets and navigation load over HTTPS.
3. Register a uniquely named test user, sign out, sign back in, and verify the session cookie is `Secure`, `HttpOnly`, and `SameSite=Strict`.
4. Upload a small supported test file, approve it as an admin, then preview and download it.
5. Trigger **Manual Deploy > Deploy latest commit** without clearing the disk.
6. After the redeploy, confirm the test user can still sign in and the test document still previews/downloads.
7. Check Render logs for a successful production bootstrap and health check. Never paste secret values into a report or ticket.

## Backup and rollback

The startup command keeps one immediate pre-deploy SQLite copy beside the live database. Copying is performed only after the previous disk-backed instance has stopped and before the new server opens SQLite.

To roll application code back, choose a prior successful deploy in Render and redeploy it. The migrations are designed to remain compatible with the prior application release. If database recovery is required, do not use Render's whole-disk snapshot restore for this custom database: Render warns that it can produce a corrupted custom database. Instead, disable automatic deploys and ship a one-time recovery release that copies `/var/data/csit-sheet.sqlite.predeploy-backup` over the live file before the server starts, verify `PRAGMA integrity_check`, then immediately restore the normal start command. Never replace a live SQLite file while the service is running. The `.predeploy-backup` is an emergency single-generation copy; add an off-service SQLite backup process before the project carries irreplaceable production data.

## Why Netlify is not used

The backend is a long-running Express server and the current persistence model is SQLite plus database BLOBs. Netlify Functions do not provide an attachable persistent SQLite disk and their request/response payload limits conflict with this application's 20 MB upload policy. Splitting only the frontend would also add cross-site cookie and CORS complexity without improving this small single-instance deployment.
